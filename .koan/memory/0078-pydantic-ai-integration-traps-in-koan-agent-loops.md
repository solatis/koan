This entry documents seven pydantic-ai library behaviors that bit koan's multi-turn agent-loop implementations (the `koan_reflect` synthesis tool, the artifact/transition tool path, and the main orchestrator/agent model-settings path). Traps 1 and 2 were distilled on 2026-04-22 after Leon root-caused an `IterationCapExceeded` failure in `koan_reflect`'s pydantic-ai loop and iterated through two successive fixes; trap 3 was added in 2026-06 while building the artifact permission gate; trap 4 was added on 2026-06-22 after Leon hit `UsageLimitExceeded` from pydantic-ai's default `request_limit` when launching scouts; trap 5 was added on 2026-06-30 after Leon root-caused an orchestrator crash where an unset `max_tokens` fell back to pydantic-ai's hardcoded Anthropic default of 4096; trap 6 was added on 2026-06-30 while implementing the phase-boundary context reset; trap 7 was added on 2026-07-03 after Leon root-caused an `AttributeError` crash in the projection fold when Ollama/DeepSeek sent tool call arguments as a JSON string.

Trap 1 -- `output_type=str` treats any plain-text model response as a valid agent termination. Pydantic-ai's default output contract accepts prose as the final result: the model runs its searches, writes its briefing as a plain-text response, and pydantic-ai exits the `async for node in run` loop cleanly without ever invoking the designated completion tool. The old raw google-genai loop in koan had an explicit text-only detection path that nudged the model back to tool use; pydantic-ai omits that nudge. The initial instinct -- simply drop `output_type=str` -- is insufficient, because pydantic-ai's default still allows text termination. The fix Leon adopted on 2026-04-22 is to close the text escape hatch explicitly: pass `output_type=TextOutput(_reject_text)` where `_reject_text` raises `ModelRetry` on every text output, forcing the model to call the designated completion tool instead of producing prose. Without this, a model update that shifts default behaviour toward direct text (as happened with Gemini in April 2026) silently breaks the loop.

Trap 2 -- `agent.iter()` does not propagate exceptions from tool handlers to user code. The old raw google-genai loop in koan used a sentinel `_DoneSignal` exception raised from the `done` tool handler and caught around the loop; the loop exited via the exception path. In pydantic-ai, tool execution happens inside `CallToolsNode` and exceptions from tool handlers are caught internally -- they never reach an `except _DoneSignal:` wrapping `async for node in run`. The fix Leon adopted on 2026-04-22: the `done` tool handler stores its structured result (citations, final briefing text, etc.) on the shared `deps` object as `_DoneResult` and returns normally; the outer loop checks `deps.done_result` after each node and breaks when it is set. Exception-based termination does not work in pydantic-ai; deps-based result handoff does.

Trap 3 -- `ModelRetry` is bounded by a per-run retry budget. `ModelRetry` is the pydantic-ai mechanism for handing a correctable error back to the model, but the Agent is constructed with a default budget of `retries=1` unless overridden, and when a tool raises `ModelRetry` more times than the budget allows pydantic-ai raises `UnexpectedModelBehavior` and the run aborts. So `ModelRetry` is unsuitable for unbounded, never-crash self-correction. koan instead returns a structured `{"ok": false, "error": {...}}` value from the tool -- a normal return, not an exception -- which has no budget and cannot crash the loop. This is the same surfacing rule trap 2 implies: return structured errors rather than raise. The artifact-mutation and workflow-transition tools were moved onto this return-envelope path in 2026-06 after a second `koan_artifact_write` to an existing draft raised and crashed a workflow.

Trap 4 -- `UsageLimits` defaults `request_limit=50`, and that cap is inherited silently whenever `usage_limits` is not passed to `Agent.iter()` / `Agent.run()`. Each `iter()`/`run()` call counts model requests from zero against the cap; on the 50th request `check_before_request` raises `UsageLimitExceeded`. koan hit this when a single scout turn made 50-plus model-request rounds. The exception is not network-transient, so koan's provider-retry classifier (`classify_provider_error` in `koan/agents/retry.py`) labels it `unexpected` and the run fails fast with no recovery. Prevention: pass `usage_limits` explicitly; koan disables the cap at every agent invocation through `build_usage_limits()` in `koan/agents/adapter.py`, which returns `UsageLimits(request_limit=None)`. This is the same genre as trap 3 -- a pydantic-ai default budget that aborts the whole run on exhaustion instead of degrading.

Trap 5 -- the Anthropic model hardcodes `max_tokens=4096` when `model_settings` does not set it (`max_tokens=model_settings.get('max_tokens', 4096)` in pydantic-ai's `models/anthropic.py`), whereas the Google, OpenAI, and Bedrock models omit the parameter and fall back to the provider's own high default. Anthropic's `max_tokens` caps TOTAL output -- thinking plus text plus tool calls -- so under `anthropic_thinking: {type: adaptive}` the model can spend the entire 4096-token budget on thinking and emit zero response text; pydantic-ai then raises `UnexpectedModelBehavior` because the response is only ThinkingParts with `finish_reason='length'`. The message reads "Model token limit (provider default) exceeded before any response was generated", which misleads: pydantic-ai formats `last_max_tokens = model_settings.get('max_tokens')`, which is `None` because koan never set it, as the literal string "provider default" -- the real ceiling sent to the API was 4096. koan never set `max_tokens` because `build_model_settings` carried only thinking and caching keys, so every Anthropic request silently got the 4096 cap. Prevention: koan now bakes an explicit, per-model-clamped `max_tokens` into `ModelSpec.settings` at flatten time (`build_resolved_model`); like trap 4, this is a pydantic-ai default that aborts the whole run when not overridden, so the fix is to always set the parameter rather than rely on the library default.

Trap 6 -- the system prompt is delivered through pydantic-ai `instructions`, not `system_prompt`, so it is re-applied to every model request and never lives in `message_history`. koan constructs every `Agent` with `instructions=options.system_prompt` (`koan/agents/pydantic_ai.py`), not the `system_prompt=` parameter. pydantic-ai applies `instructions` fresh on each `ModelRequest` via `_get_instructions` in `_agent_graph.py` (mapped to the provider's system field, e.g. Anthropic's top-level `system`), whereas `system_prompt` is materialized as a `SystemPromptPart` added to the first request ONLY when `message_history` is empty (the `UserPromptNode._sys_parts` path). Because koan uses instructions, two things follow that an agent reasoning about the loop gets wrong if it assumes `system_prompt` semantics: (a) clearing or rebuilding `message_history` does NOT drop the system prompt -- it is re-applied on the next request regardless of history; and (b) the "system prompt is added only when message_history is empty" rule does not apply to koan at all, since koan never stores a `SystemPromptPart`. This bit the planning of the phase-boundary context reset on 2026-06-30: the intake brief froze a constraint that clearing `message_history` would drop the system prompt and that the reset must extract and re-establish a `SystemPromptPart`. Reading the agent construction at plan time corrected it -- the reset just clears `message_history` to `[]` and the instructions re-apply -- avoiding a dead extract/synthesize-`SystemPromptPart` code path. Prevention: when reasoning about message-history clearing, compaction, or context surgery in koan, treat the system prompt as instructions re-applied per request, not as content stored in history.

Trap 7 -- `ToolCallPart.args` is typed `str | dict[str, Any] | None` in pydantic-ai, not always `dict`. koan's `StreamEvent.tool_args` field in `koan/agents/events.py` is typed `dict | None` and receives `part.args` un-normalized at two construction sites in `koan/agents/loop.py`: the `tool_start` emission and the `PartEndEvent` `tool_input_delta` emission. When a provider sends args as a JSON string — Ollama/DeepSeek does this, and Gemini likely does — the string flows through `build_tool_request` in `koan/events.py` into `payload["args"]`, then into `_make_exploration_entry` in `koan/projections.py` where `ti = tool_args or {}` keeps the truthy string, and `ti.get("pattern", "")` crashes with `AttributeError: 'str' object has no attribute 'get'`. The same vulnerability exists in the `tool_input_delta` fold case. Prevention: normalize `part.args` at the `StreamEvent` construction boundary using `isinstance` check → `json.loads` → fallback `{"raw": raw_args}` on `JSONDecodeError` or `TypeError`, following the existing pattern at `koan/projections.py:1531-1535`. Without this, any provider that sends string-encoded tool args crashes the projection fold and breaks frontend rendering of tool calls.

Leon noted on 2026-04-22 that with traps 1 and 2 known upfront, building a new pydantic-ai agent loop in koan is roughly a 5-minute edit; without them it takes a ~20-minute investigation because trap 2 only manifests after trap 1 is fixed. The underlying project invariant reaffirmed on the same day: koan accepts structured agent output via tool calls with typed arguments, not via parsing the model's last message.
