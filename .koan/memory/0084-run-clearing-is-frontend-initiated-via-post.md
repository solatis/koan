Run-clearing lifecycle in the koan workflow engine -- Leon reversed the 2026-04-23 decision that made run clearing frontend-initiated (a 3-second timer plus nav-click handlers calling `POST /api/run/clear`). The backend now owns the full end-of-workflow reset: a shared helper `finalize_workflow_end(app_state)` in `koan/state.py` clears the interaction buffers (`user_message_buffer`, `steering_queue`) and the frozen run config/credential/model state, then emits `run_cleared` -- called from `apply_set_phase`'s `done` branch in `koan/tools/koan_tools.py` (covering both the `koan_set_phase` tool path and the mechanical `POST /api/phase` HTTP path) and from `driver_main`'s failure-exit branch in `koan/driver.py`. The event order is `yield_cleared` -> `workflow_completed` -> `run_cleared`, so the completion folds into the projection before the run clears and the frontend's rising-edge `lastCompletion` snapshot still captures the banner. `POST /api/run/clear`, the frontend 3s timer, and the `clearRun` client wrapper were deleted; the UI navigates to the front page on the run falling edge (projection `run` becoming null). Root cause of the reversal: the frontend-owned clear left the server-side run state live after completion, so starting a new workflow before the frontend sent the clear produced a 409 Conflict from `api_start_run`. The residual winding-down race (loop return -> subagent teardown -> driver exit still in flight when the user clicks start) is closed in `api_start_run`: when `projection.run is None` but `driver_task` is still pending, the route awaits the shielded task with a 10s timeout instead of rejecting. The double `workflow_completed` push was resolved by keying the driver's push on `not workflow_done` -- the `done` path's completion event is owned solely by `apply_set_phase`; the driver covers crash/abnormal exits (and calls `finalize_workflow_end` there too, so failed runs no longer strand the UI). `finalize_workflow_end` deliberately does NOT reset `run.workflow_done` (the loop's termination check reads it; `api_start_run` resets it) and does NOT touch `yield_future` (owned by its resolution sites). Alternatives rejected: keeping `/api/run/clear` for UI timing while decoupling backend state (two owners of the reset); patching only the 409 guard (leaves the frontend dependency in place); lazy `run_cleared` emission at next start-run or after a backend delay (the UI must reach the front page immediately).
