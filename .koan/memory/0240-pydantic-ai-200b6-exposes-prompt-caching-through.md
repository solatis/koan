In pydantic-ai 2.0.0, prompt caching is configured by model-class-specific `model_settings` keys whose names differ per class -- there is no single cross-provider caching switch, and the model profiles expose no prompt-caching capability flag (so koan owns that knowledge in `koan/agents/model_catalog.py`). `AnthropicModel` reads `anthropic_cache` (a top-level auto-advancing breakpoint over the message prefix that moves forward as the conversation grows, counts as 1 of Anthropic's cache slots, auto-trims excess, and is mutually exclusive with `anthropic_cache_messages`), plus `anthropic_cache_instructions` (system prompt) and `anthropic_cache_tool_definitions` (tool schemas). `BedrockConverseModel` reads different keys -- `bedrock_cache_messages`, `bedrock_cache_instructions`, `bedrock_cache_tool_definitions` -- emitting `cachePoint` blocks, and it folds cache tokens into `input_tokens` while still reporting `cache_read` separately. The provider-agnostic `pydantic_ai.messages.CachePoint(ttl=Literal['5m','1h'], default '5m')` is translated to Anthropic `cache_control` (`anthropic.py` `_add_cache_control_to_last_param`) and Bedrock `cachePoint` (`bedrock.py` `_get_cache_point`) at its exact wire position; per-CachePoint TTL is honored on both. A CachePoint may NOT be the first content in a user message -- both `AnthropicModel` and `BedrockConverseModel` raise -- so it must attach to a message that already carries text. Cache-breakpoint budget: Anthropic's `MAX_CACHE_POINTS` is 4, reduced to 3 when the top-level automatic `anthropic_cache` is active (it reserves one slot implicitly); with system-instructions + tool-definitions + one artifact CachePoint the budget is fully consumed at zero headroom, and excess message points are trimmed newest-first (a second message point would trim the older one). Bedrock's `MAX_CACHE_POINTS` is 4. On a phase's first turn (no conversation tail yet) the Bedrock `bedrock_cache_messages` tail breakpoint and an inline artifact CachePoint collapse onto the same last-user-message block and pydantic-ai dedups so one TTL survives -- benign; from turn 2 they occupy distinct blocks with independent TTLs. `OpenRouterModel` extends `OpenAIChatModel`, has no caching path, and the OpenAI base filters out `CachePoint`, so there is no supported way to drive OpenRouter prompt caching through pydantic-ai. Google and OpenAI cache automatically server-side and report cache reads via `RequestUsage.extract` (Google's `cached_content_token_count` and OpenAI's `cached_tokens` both map to `cache_read_tokens`); neither exposes a 5m/60m per-request TTL selection through pydantic-ai. Google explicit caching is exposed only as `google_cached_content: str` -- a reference to a pre-created server-side cached-content resource made via `client.caches.create(..., ttl=...)` with its own name/expiry/invalidation lifecycle, NOT a per-request breakpoint, which is why per-request Gemini caching is a distinct, larger piece of work. OpenAI exposes only `openai_prompt_cache_key: str` (a routing hint) and `openai_prompt_cache_retention: Literal['in_memory','24h']` -- no explicit short/long TTL knob. This matters because any koan change to caching must emit the transport-correct keys and honor these constraints; passing Anthropic keys to a Bedrock or OpenRouter model silently caches nothing.
